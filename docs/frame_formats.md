# Toshiba AB protocols frame formats

This component can read several related Toshiba AB-bus protocols or frame formats. The default
configuration is `frame_format: auto`, which starts in the most common TCC-Link protocol
mode and switches to a more specific format if the component can identify one from live
traffic. Not all protocols are automatically identified.

## Quick selection guide

| `frame_format` value | Format | Typical use | UART parity | Auto-detected? | Notes |
| --- | --- | --- | --- | --- | --- |
| `auto` | Automatic | Recommended first try for most installs | See target format | N/A | Default. Starts as normal TCC-Link and confirms `normal` from traffic. |
| `n`, `normal`, `tcc-link` | Classic TCC-Link | Most central HVAC systems using the AB bus | `EVEN` | Yes | The component confirms this when it sees a valid master keepalive. |
| `hm` | HM / newer RAV-RM  | Newer HM-range/RAV-RM indoor units | `EVEN` | Maybe | Uses an `A0:00` prefix and different source/destination byte positions, then is normalised internally. |
| `a0`, `estia_a0` | Estia R32 protocol | R32 Estia heat pumps | `EVEN` | No, set explicitly | Very similar to HM, Uses two-byte CRC-16. |
| `u`, `tu2c`, `wrapped` | TU2C protocol | Newer U-series HVAC systems | `NONE` | No, set explicitly | Fully supported. Frames are prefixed with `F0:F0` and have a trailing `A0`. |
| `estia` | Estia R410A (first gen) TU2C variant | R410A Estia heat pumps | `NONE` | No, set explicitly | Uses the TU2C reader path and Estia-specific control/decoding logic. |

## Common fields used by frames

TCC-Link and the component's internal representation of frames (messages) use this
layout:

```text
SRC:DST:OPCODE1:LEN:DATA[0..LEN-1]:CRC
```

- `SRC` and `DST` are 8-bit source and destination addresses. Common values are
  `0x00` for the master/indoor unit and `0x40` for a wall remote or this ESP
  when emulating one. If `master` is omitted from YAML, the component keeps
  address auto-detection enabled and seeds the master address from the selected
  frame format (`0x00` for normal/HM/A0, `0x90` for TU2C, and `0x70` for
  first-generation Estia); an explicit `master` value is never overwritten by
  auto mode.
- `OPCODE1` identifies the broad message type, for example `0x10` ping,
  `0x11` parameter/status command, `0x15` read envelope, `0x18` ACK, `0x1A`
  sensor value, `0x1C` status, `0x55` temperature report, or `0x58` extended
  status.
- `LEN` is the number of data bytes between `LEN` and `CRC`.
- `CRC` is the classic one-byte checksum used by the existing TCC-Link decoder.

Example frames seen or generated by the component:

```text
01:52:11:04:80:86:A1:05:E4      # master parameter/status-style frame
01:52:11:04:80:86:48:01:09      # classic status example
40:00:15:07:08:0C:81:00:00:48:00:9F  # remote read/status envelope
42:00:11:04:08:89:<TEMP>:46:<CRC>    # external/room temperature report shape
```

External room-temperature reports always use source address `0x42`. The
wall-remote auto-addressing sequence skips `0x42` when resolving a collision so
that normal remote traffic cannot claim the temperature sensor's reserved
address.

## `normal` / classic TCC-Link

### Structure

```text
SRC:DST:OPCODE1:LEN:DATA...:CRC
```

The reader takes the fourth byte as `LEN`, expects `4 + LEN + 1` total bytes,
and validates the one-byte CRC. With the default frame filter enabled it ignores
obvious invalid normal frames whose first byte is greater than `0xA0`, which is
usually caused by electrical noise in the line, unless `filter_frames` is set to `false`.

CRC failure logs include the received checksum, the checksum calculated from the
captured bytes, and their XOR `syndrome`. A syndrome with one bit set is consistent
with a single-bit error somewhere in the frame (the XOR checksum cannot identify
which byte); a stable syndrome suggests a repeatable bit error, while changing
syndromes suggest broader signal-integrity or sampling problems.

### Auto-detection

Yes. When `frame_format: auto` is used, the reader initially parses frames as
classic TCC-Link. The component confirms the protocol after it receives a valid
master keepalive/ping frame.

### YAML

```yaml
uart:
  tx_pin: GPIO12
  rx_pin: GPIO13
  baud_rate: 2400
  parity: EVEN
  rx_buffer_size: 2048

climate:
  - platform: toshiba_ab
    name: "Toshiba AC"
    frame_format: auto   # default option, and can be omitted; or forced with: normal
```

## `hm` / HM-range systems

### Structure

Some HM/RAV-RM master systems send frames with a different structure in the frame format, and
with some extra bytes, for example:

```text
A0:00:OPCODE1:LEN:00:SRC_MODE:SRC:DST_MODE:DST:00:OPCODE2:PAYLOAD...:CRC
```

`LEN` is the number of data bytes between `LEN` and `CRC`
The values of bytes and their meaning is consistent with the TCC-Link protocol, but they are in different
positions. The firmware reader "converts" the read messages to the TCC-Link format and uses most of the
same code for interpretation.
However, CRC validation for HM frames is intentionally not checked because the HM CRC
algorithm has not yet been identified.

To send messages, the firmware just uses the normal TCC-Link format and the frames are accepted by the master.

### Auto-detection

Yes. In `auto` mode the component confirms `hm` when it sees a valid HM-shaped
frame from the master address.

### YAML

```yaml
uart:
  tx_pin: GPIO12
  rx_pin: GPIO13
  baud_rate: 2400
  parity: EVEN
  rx_buffer_size: 2048

climate:
  - platform: toshiba_ab
    name: "Toshiba HM AC"
    frame_format: auto   # default; or force with: hm
```

## `tu2c` / "U" series systems

### Structure

TU2C frames are easily identified by a two-byte prefix and one-byte suffix:

```text
F0:F0:TOTAL_LEN:SRC:DEST:C0:DATA...:CRC:A0
```

`TOTAL_LEN` includes the two `F0` prefix bytes, the length byte itself, and the
trailing `A0`. After the length byte, the reader stores the following bytes up
to but not including the final `A0` as the frame payload to decode messages.
TU2C command examples:

```text
F0:F0:0B:50:90:C0:01:21:02:CF:A0  # power-off example
F0:F0:0A:50:90:C0:49:0D:00:A0     # registration/query example
F0:F0:0C:50:90:C0:41:5C:90:F3:CC:A0  # keepalive example
```

### Auto-detection

No. The component knows how to interpret this format when selected, but `auto` does
not currently scan for TU2C protocol. Set it explicitly.

### YAML

```yaml
uart:
  tx_pin: GPIO12
  rx_pin: GPIO13
  baud_rate: 2400
  parity: NONE
  rx_buffer_size: 2048

climate:
  - platform: toshiba_ab
    name: "Toshiba TU2C AC"
    frame_format: tu2c   # aliases: u, wrapped
```

## `a0` / Estia R32 protocol

### Structure

The Estia R32 AO protocol is not the same as classic TCC-Link, even though it
uses the same AB-bus speed and even parity and the frames resemble the HM protocol.
A full frame looks like:

```text
A0:00:TYPE:LEN:00:SRC_MODE:SRC:DST_MODE:DST:DTYPE_H:DTYPE_L:DATA...:CRC_H:CRC_L
```

`SRC_MODE:SRC` and `DST_MODE:DST` are also referred as `SRC_H:SRC_L` and `DST_H:DST_L` 

The component processes bytes after the `A0:00` prefix. `LEN` is the
number of bytes between `LEN` and the two-byte CRC. The CRC is CRC-16/MCRF4XX
over the `A0:00` prefix plus the stored frame bytes except for the final CRC bytes.

Common SRC and DST addresses are `0x00` for the master, `0x40` for the remote, `0x41`
for the optional 0-10 V demand interface emulation, and `0xFE` for broadcast. Consistent
with Toshiba conventions.

The optional one-byte `remote:` and `master:` YAML values are also used for A0
without requiring separate A0 address options. The remote value is zero-extended
(`remote: 0x40` becomes `0x0040`, written as `00:40`) and the A0 master mode byte
`0x08` is prepended to the master value (`master: 0x00` becomes `0x0800`, written
as `08:00`). If omitted, those same `0x40` and `0x00` defaults apply.

Example frames:

```text
A0:00:11:08:00:00:40:08:00:00:41:22:<CRC_H>:<CRC_L>  # power-off command
A0:00:11:08:00:00:40:08:00:03:C0:02:<CRC_H>:<CRC_L>  # mode command (heat)
A0:00:15:0A:00:00:40:08:00:00:E8:C0:01:00:<CRC_H>:<CRC_L>  # data request
A0:00:18:26:00:SRC_H:SRC_L:DST_H:DST_L:00:E8:C1:01:00:DATA...:CRC_H:CRC_L
```

### Auto-detection

Yes. In `auto` mode, the component watches the byte stream for a complete
`A0:00` frame with a valid CRC-16 and master source address `0x0800`; it then
confirms `frame_format: a0`. Because Estia installs often need Estia-specific
options too, the Estia example forces `a0`.

### YAML

```yaml
uart:
  tx_pin: GPIO15
  rx_pin: GPIO13
  baud_rate: 2400
  parity: EVEN
  rx_buffer_size: 2048

climate:
  - platform: toshiba_ab
    name: "Toshiba Estia"
    frame_format: a0
    filter_frames: false
    autonomous: true       # optional: poll E8:C0/E8:C1 without another gateway
    demand_enabled: false  # optional: 0-10 V demand emulation
```

## `estia` / first-generation Estia R410A

### Structure

The `estia` option selects the component's first-generation Estia support path.
When `master` is omitted, this format defaults the master address to `0x70`
and keeps address auto-detection enabled.
It uses the TU2C-style format rather than the Estia R32 A0 style and parity NONE:

```text
F0:F0:TOTAL_LEN:SRC:DEST:DATA...:CRC:A0
```
`TOTAL_LEN` includes all bytes

Example frames:

```
F0:F0:11:70:FF:E0:C0:31:C3:80:10:90:52:66:00:EC:A0      Status frame
F0:F0:0B:60:70:E0:01:21:0C:E9:A0      Domestic Hot Water ON command
```

Internally, first-generation Estia and TU2C protocol use most of the same code.

### Auto-detection

No. Set `frame_format: estia` explicitly if you are using this.

### YAML

```yaml
uart:
  tx_pin: GPIO12
  rx_pin: GPIO13
  baud_rate: 2400
  parity: NONE
  rx_buffer_size: 2048

climate:
  - platform: toshiba_ab
    name: "Toshiba Estia first gen"
    frame_format: estia
    zone1_switch:
      name: "Estia Zone 1"
    dhw_boost:
      name: "Estia DHW Boost"
```

### Zone 1 mode command encoding

`estia_mode_encoding` optionally selects the two payload bytes in the
`E0:01:22` mode command. It requires `frame_format: estia`.

| Setting | Cool payload | Heat payload |
| --- | --- | --- |
| `"05_06"` (default) | `22:05:05` | `22:06:06` |
| `"01_02"` | `22:01:01` | `22:02:02` |

```yaml
climate:
  - platform: toshiba_ab
    name: "Estia DHW"
    frame_format: estia
    estia_mode_encoding: "01_02"
    zone1_climate:
      name: "Estia Zone 1"
```

The default payloads were reported in [issue #90](https://github.com/makusets/esphome-toshiba-ab/issues/90).
The alternate payloads were captured from an HWS-P1105XWHM3-E R410A wall
controller. The meaning of the extra `0x04` in each default payload byte is
unknown; cooling permission, DHW and zone settings do not establish which
encoding to select. Choose the alternate only when controller captures match.
Both settings use the same protocol and compute the checksum with the current
remote/master addresses.

Power commands, startup sequencing, read-only behavior and weather compensation
are unchanged. Auto uses the selected Heat payload after enabling weather
compensation. The alternate encoding has packet-level software tests; sustained
ESPHome operation and Auto still need hardware validation.

## Configuration aliases

The accepted values for `frame_format` are:

```text
auto
n, normal, tcc-link
hm
u, tu2c, wrapped
a0, estia_a0
estia
```

If you are unsure, start with the default `auto` and `parity: EVEN`. If your unit
is known to be a U-series/TU2C system, use `parity: NONE` and
`frame_format: tu2c`.

## Remote address selection

The component uses one remote address for the selected protocol. Without an
explicit YAML `remote`, TCC-Link/HM starts at `0x40`, TU2C at `0x50`, and
first-generation Estia at `0x60`. Setting `remote` explicitly disables automatic
collision recovery.

TU2C detects collisions from valid received remote frames after filtering its own
TX echo. It advances through `0x50`–`0x59`, skipping reserved address `0x52`, and
registers the replacement address. Like TCC-Link, it stops advancing at the upper
address limit and suppresses remote transmissions if no unused address remains. Commands queued under the collided TU2C address are discarded.
Registration ACKs must target the current remote address.

TU2C remotes seen during the initial discovery period appear in the existing
remote count and remote address text sensors, including remotes identified from
frames other than keepalives.

All protocols stay silent for the first 40 seconds after component startup while
processing incoming bus traffic. TCC-Link/HM, TU2C, and first-generation Estia remember occupied remote
addresses, including addresses heard before a collision at their current
candidate. Automatic address selection skips those occupied addresses and the
reserved temperature-sensor address where applicable (Estia retains its full
`0x60`–`0x69` range). Registration is built using the selected
address after the silent period; startup registration requests are not queued
with an earlier candidate. Collision recovery stays active afterward.

### Regular TU2C remote temperature reports

The header remote (`0x50`) sends a regular temperature report at `ping_interval`
(default 30 seconds), independently of the independent-sensor reporting option:

```text
F0:F0:0D:50:<MASTER>:C0:61:38:<FLAG>:<TEMP>:00:<CRC>:A0
```

`TEMP = (°C + 35) × 2`; `CRC` is the additive checksum of the bytes from
`0D` through the trailing `00`. A valid configured temperature sensor supplies
the reading. Otherwise the report uses current temperature minus 0.5 °C, then
target temperature, then 20 °C. `FLAG` is always `01`, regardless of temperature
source: regular TU2C header-remote reports start with `61:38:01`. Only address `0x50` reports: automatic
collision recovery to another address disables these reports. Startup silence,
read-only mode, and autonomous registration gating also apply.

Incoming `61 38` reports are logged with their sensor flag. The unit's status
frames remain the source of control-temperature state. This regular report is
distinct from the independent temperature sensor mechanism; it does not
implement TU2C independent-sensor reporting. See
[PR #256](https://github.com/makusets/esphome-toshiba-ab/pull/256) for the captured
frame and sensor-flag evidence.
